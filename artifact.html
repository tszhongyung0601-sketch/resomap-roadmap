02為什麼這樣拆

這份路線圖不是把功能分成六桶，而是把依賴圖拓撲排序之後自然斷開的位置，再套上一條資源容量規則。

第一個事實：T0 是既成事實，由程式碼盤點讀出，不是計畫。它放今天真的跑得動的東西——四個純函式引擎（時間位移調整、共識統計、分帳結算、haversine 距離）、真實 OSM 圖磚、瀏覽器原生語音合成，以及一個今天就會渲染的「商業模式」畫面。但 T0 的說法必須修正：它不是「不編造任何數字」，而是「每一個示意值都在畫面上當場標示為示意值」。播放數、喜歡數、價格、成交與佣金全部是標示過的示意值，投票不會回寫，抵達偵測必須手動觸發。誠實是這份文件唯一的差異化資產，第一階就自我拔高，後面每一句都會被逐句查證。

第二個事實：這個產品最大的洞是「規劃」那一段是空的——CreateTrip 問完五題後 who／likes／invitees 全部丟棄，只產出五天空行程。所以 T3 的 itinerary-generator 是規劃鏈的軸心。它不能更早：要排出一天的動線，必須同時有夠多景點（T2）、真實路網時間（T2）與真日期（T1）。任何把 AI 規劃排進 T1 的版本，都是在沒有景點庫與路網時間的情況下叫模型硬編行程。

第三個事實：變現鏈的第一節是行政不是工程。affiliate-accounts 零工程量卻要等審核，所以 T1 送件；通過後 T2 的 real-deep-links 只是把追蹤碼接上，是全圖投報率最高的一段。但第一筆佣金是結果不是里程碑——T2 可被驗收的是「連結真的帶得動追蹤碼」。

第四個事實：主動性排在可信度後面。adapt-auto-trigger 要四個訊號同時為真，缺一就誤判，而誤判比不提醒更傷。在使用者沒打開 App 時主動推商業訊息，還要先有打擾規則與背景定位（T4），所以 in-trip-deals 落在 T5——物理順序，不是保守。

第五件事是這一版新增的容量規則：同一階的工程量以「最多 1 項 XL、3 項 L」為規劃上限，非工程門檻項目（編輯部產能、地推業務、供應商合約）不計入。依此規則，T3（itinerary-generator／adapt-auto-trigger／content-cms 三個 XL）與 T4（realtime-sync／price-inventory-feed 兩個 XL 加三個 L）都超載，必須在階段內跑兩波：T3 第一波做生成與自動觸發，第二波做內容後台與雲端房；T4 第一波做對帳與群組，第二波做原生能力與金流。這是明說的超載，不是藏起來的。

最後必須誠實交代格式限制：這份 schema 只有六格，而依 T4 的原始體積它應該是七階。實際的處理是把原本的 T4 切成兩段（T4＝對帳與群組、T5 前半＝內容與金流規模化），而原本 T5 那四項非工程門檻的收入選項只能併進 T5 後半。因此 T5 不是一個工程階段，而是三條互不相干的軌道並排：MODEL B 完成式（工程）、內容與金流規模化（工程＋編輯部）、非工程門檻的收入選項（業務、創作者、供應商合約、使用者量體）。實際排程時 T5 必須至少再拆成兩階，把它們畫在同一條進度曲線上是這份文件最容易誤導人的地方。

換句話說：T1 修不能說謊的地方並開始等審核，T2 打地基並讓外導可歸因，T3 補上規劃的洞讓 MODEL B 第一次有資料可讀，T4 讓錢對得回一次點擊、讓群組真的能用，T5 才有資格談 MODEL B 的完成式與多條收入線。

先講清楚一件事：這份路線圖有三條並行的依賴鏈，不是一條七段的主鏈。實際逐邊計算 86 個節點的最長路徑，最長只有 5 個節點（4 條邊），而且並列三條——(1) 後端資料庫 → 使用者帳號 → 原生 App 上架 → 背景定位 → 途中情境優惠；(2) 後端資料庫 → 使用者帳號 → 伺服器歸因 → 佣金對帳 → 營收後台；(3) 後端資料庫 → 真實路線／天氣資料源 → 異常自動偵測 → 打擾規則 → 途中情境優惠。三條鏈共用同一個根（backend-db），在 T4／T5 交會於 in-trip-deals 與 revenue-dashboard。

規劃鏈是第四條、也是較短的一條：後端資料庫 →（景點資料庫＋真實路線＋真實日期）→ AI 行程生成 → 行程情境推薦與缺住宿提醒。必須明說：itinerary-generator 的 depends_on 是 real-trip-dates／poi-database-backend／live-routing-eta，並不含 user-accounts 或 trip-cloud-sync——生成一份行程本身不需要帳號，需要帳號的是把行程存起來、跨裝置看得到、以及認得出是誰點了那個連結。poi-database-backend、itinerary-generator、in-trip-deals 三者不在同一條依賴鏈上。

變現鏈：affiliate-accounts（純行政、審核要等、可能被拒，所以 T1 就要送件）→ real-deep-links → server-side-attribution → postback-reconciliation → revenue-dashboard。注意 server-side-attribution 真的依賴 real-deep-links 與 analytics-pipeline：沒有帶得動追蹤碼的深連結就沒有東西可以掛點擊編號，沒有事件收件端就收不到點擊。

獲客鏈（原本完全缺席，補上）：PWA 公開網址（T1，同時也是聯盟審核要看的東西）→ 種子使用者（T2，來源必須明列：既有社群 N 人、台南在地社團、實地陪走測試 M 場）→ 商店上架（T3）→ 旅後分享頁與 SEO（T5）→ 邀請迴圈與範本市集（T4／T5）。沒有這條鏈，T2 的第一塊錢、T4 的 A／B 分流、T5 的 B2B 與贊助版位全部沒有分母；risks 裡「聯盟可能因為沒有上架、沒有使用者而被拒」本身就是這條鏈是前置條件的證據。

以「敘事順序」而非依賴順序來說（這是給人聽的版本，不是拓撲排序）：修可信度 → 打地基 → 認得出人並收到第一塊錢 → 補上規劃的洞 → 讓錢對得起來、讓群組真的能用 → 讓 MODEL B 每天在街上發生。這兩種順序不可混用，混用就是把敘事講成因果。

這一階要做到

把一條完整的旅程敘事從探索走到交棒外導，全程可點、可驗證，且每一個示意值都在畫面上當場標示為示意值。
